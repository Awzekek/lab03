# Анализ и моделирование данных предметной области

## 1\. Описание предметной области

**Предметная область:** сервис бронирования авиабилетов Aviasales, вариант 10.

**Назначение:** поиск и сравнение вариантов перелёта по направлению, датам и количеству пассажиров. Сервис агрегирует предложения авиакомпаний и продавцов и направляет пользователя к продавцу для завершения оформления.

**Основные пользователи:**

* путешественник — выполняет поиск и выбирает подходящий перелёт;
* пассажир — совершает перелёт;
* авиакомпания — выполняет рейсы;
* агентство или продавец билетов — предоставляет предложения и оформляет бронирование;
* оператор сервиса — обеспечивает работу информационной системы.

**Основные процессы:**

* поиск перелётов по заданным параметрам;
* получение и сравнение предложений;
* просмотр информации о рейсах, аэропортах и авиакомпаниях;
* выбор подходящего предложения;
* переход к продавцу для оформления;
* бронирование и оформление билетов у продавца.

**Основные задачи информационной системы:**

* предоставление пользователю удобного поиска авиабилетов;
* сбор и отображение предложений разных продавцов;
* предоставление информации о маршрутах и расписании;
* сравнение стоимости и условий перелёта;
* направление пользователя к продавцу для завершения оформления.

Модель является аналитической концептуальной моделью предметной области и не утверждает, что точно повторяет внутреннюю структуру базы данных Aviasales.

## 5\. Связи между объектами

|Объект 1|Объект 2|Тип связи|Смысл|
|-|-|-|-|
|User|Search|1:N|Пользователь может выполнять множество поисков; поиск также может быть анонимным|
|Search|Offer|1:N|Один поиск возвращает множество предложений|
|Airline|Flight|1:N|Одна авиакомпания выполняет множество рейсов|
|Airport|Flight (отправление)|1:N|Из одного аэропорта отправляется множество рейсов|
|Airport|Flight (прибытие)|1:N|В один аэропорт прибывает множество рейсов|
|Seller|Offer|1:N|Один продавец предоставляет множество предложений|
|Offer|Flight|M:N|Предложение может включать несколько сегментов, а один сегмент может встречаться в разных предложениях|
|Offer|Booking|1:0..1|Предложение может быть выбрано для оформления бронирования|
|Seller|Booking|1:N|Один продавец может оформлять множество бронирований|
|Booking|Ticket|1:N|Одно бронирование может содержать билеты нескольких пассажиров|
|Passenger|Ticket|1:N|Одному пассажиру могут оформляться билеты|
|Flight|Ticket|1:N|На один сегмент рейса может быть оформлено множество билетов|

Для связи Offer–Flight типа M:N в детализированной логической модели можно было бы использовать промежуточную сущность «Сегмент предложения». Реализация таблиц в рамках данной лабораторной работы не требуется.

## 6\. Концептуальная модель данных

Для отображения структуры предметной области строится ER-диаграмма. Она включает сущности User, Search, Passenger, Flight, Airport, Airline, Offer, Seller, Booking и Ticket, их основные атрибуты и связи с указанием кратности.

Модель отражает следующий сценарий: пользователь выполняет поиск, получает предложения, предложения состоят из сегментов рейсов, рейсы связаны с аэропортами и авиакомпаниями. После выбора подходящего предложения пользователь переходит к продавцу для оформления бронирования и билетов.

Диаграмма создаётся в draw.io и экспортируется в PNG. Редактируемый исходник диаграммы сохраняется отдельно.

## 7\. Оценка качества исходных данных

**1. Достаточно ли объектов выделено?**

Для основного сценария поиска и выбора перелёта выделенных сущностей достаточно. В модели представлены поисковые запросы, предложения, рейсы, аэропорты, авиакомпании, продавцы, бронирования и билеты.

**2. Отсутствуют ли важные сущности?**

Для расширенной модели можно добавить тариф, багаж, платёж, возврат и дополнительные услуги. В текущей модели они не выделены, поскольку не являются обязательными для рассмотрения базового сценария.

**3. Все ли необходимые атрибуты определены?**

Основные атрибуты объектов указаны. Детальные данные документов пассажиров не описаны, поскольку требования к ним зависят от продавца, перевозчика и направления перелёта.

**4. Имеются ли дублирующиеся данные?**

Дублирование названий аэропортов, авиакомпаний и продавцов возможно. Для уменьшения дублирования они вынесены в отдельные сущности, а в связанных объектах используются идентификаторы и коды.

**5. Достаточно ли информации для дальнейшего проектирования информационной системы?**

Полученная модель может служить основой для дальнейшего проектирования. Перед реализацией необходимо уточнить обязательность полей, правила уникальности, обработку пересадок, валют и статусов.
